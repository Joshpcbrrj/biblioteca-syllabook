# Dossiê c07 · Volumes no Compose

## Fatos (conferidos em 2026-11-20) — https://docs.docker.com/reference/compose-file/volumes/ · https://docs.docker.com/reference/cli/docker/compose/down/
- Volume nomeado `db-data` vira `{project_name}_db-data`
- `name:` é usado como está, sem prefixo do projeto
- `external: true`: o Compose não cria e dá erro se faltar
- `down` não remove volumes; `down -v` remove os nomeados da seção volumes e os anônimos

## Erros comuns
- `down -v` por hábito e perda dos dados do banco
- Bind mount escondendo a pasta da imagem

## Testado (Compose v5.7.0, 2026-11-21), projeto contador
- Sem volume: postgres:17 cria volume anônimo (hash) em /var/lib/postgresql/data; `down` o deixa como sobra; `down -v` o remove sem imprimir linha `Volume`
- Volume nomeado `db-data` -> `contador_db-data`; `down` não imprime `Volume`; contagem 1, 2, down/up, 3
- `down -v` -> `Volume contador_db-data Removing/Removed`; próximo up: 1
- Volume não declarado -> `service "db" refers to undefined volume db-data: invalid compose project`
- Montar em /var/lib/postgresql (17) -> dados vão para o anônimo; contagem volta a 1
- Bind `./vazio` inexistente: Docker cria a pasta vazia; nginx responde 403 Forbidden; `:ro` -> `Read-only file system`
- Pasta renomeada para visitas-app -> `Volume visitas-app_db-data Created`; com `name: contador`, reaproveita contador_db-data

## Windows com WSL (acréscimo de 2026-11-21) — https://docs.docker.com/desktop/features/wsl/best-practices/
- Página "WSL 2 best practices for Docker Desktop on Windows", seção "Optimise file system performance with bind mounts": usar bind mounts a partir do sistema de arquivos do Linux, não do Windows; "Linux containers only receive file change events ... if the original files are stored in the Linux filesystem"; "Performance is much higher when files are bind-mounted from the Linux filesystem"; exemplo `docker run -v ~/my-project:/sources <my-image>`, evitar `/mnt/c`.
- Testado (Windows 11, Docker Desktop, WSL 2 Ubuntu 26.04.1, kernel 6.18.58.1-microsoft-standard-WSL2):
  - Shell do WSL, 2.000 arquivos pequenos: `~/projetos` criar 141 ms / ler 42 ms; `/mnt/c/Users/<usuário>` criar 7.035 ms / ler 9.773 ms.
  - Docker Desktop no Windows, pasta de C: montada em alpine:3.20 com `inotifyd - /dados`: mudanças feitas pelo Windows não geraram evento; `echo d >> /dados/a.txt` dentro do contêiner gerou `r`, `c`, `w`.
- (Antes da integração WSL ligada: contêiner pelo WSL não testado.) Testado depois, ver abaixo.

## Testado pelo WSL (2026-11-21, integração WSL ligada, usuário josh, Compose v5.7.0 / Engine 29.9.3)
- Projeto `testebind`: nginx:1.27-alpine com `./site:/usr/share/nginx/html:ro` + alpine:3.20 `inotifyd - /dados` na mesma pasta. Rodado pelo shell do WSL.
- `~/projetos/teste-bind`: edição pelo WSL -> nginx vê v2 e eventos `c`, `w`; edição pelo Windows (`//wsl.localhost/Ubuntu-26.04/home/josh/...`) -> nginx vê v3 e eventos `c`, `w`. Dentro do contêiner, 2.000 arquivos: criar `real 0m 0.08s`, ler `real 0m 0.01s`.
- `/mnt/c/Users/<usuário>/teste-livro/teste-bind`: edição pelo WSL -> nginx vê v2 e eventos `c`, `w`; edição pelo Windows (`C:\...`) -> nginx vê v3, nenhum evento de escrita (só `r a 0` das leituras do `cat`). 2.000 arquivos: criar `real 0m 4.85s`, ler `real 0m 4.20s`.
- Arquivos criados pelo contêiner em `~/projetos` ficaram com dono root: `rm: cannot remove ... Permission denied` para o usuário josh; apagados com root.
