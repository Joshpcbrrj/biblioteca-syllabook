# Dossiê c01: Por que contêineres existem
Original: seções "na minha máquina funciona", contêiner × VM, imagem × contêiner, o que isola, o que é o Docker, quando NÃO usar. Conferido em 2026-11-26.

## Fatos
- Docker Engine/CLI de referência: 29.9.3, API 1.56 (`docker version` nesta máquina, 2026-11-26). Desktop CLI plugin 4.99.0. Última do Desktop publicada: 4.100.1 (2026-11-23). https://docs.docker.com/desktop/release-notes/
- Engine 29.x: série atual; notas em https://docs.docker.com/engine/release-notes/29/ (2026-11-26).
- Contêiner = processo isolado; isolamento por namespaces e cgroups; kernel compartilhado com o host. https://docs.docker.com/get-started/docker-overview/ (a conferir ao escrever).
- No Windows/Mac o Desktop roda uma VM Linux; no Windows, pelo WSL 2 (kernel observado aqui: `6.18.58.1-microsoft-standard-WSL2`, hostname do engine `docker-desktop`). Rodar `uname -r` fora e dentro mostra o mesmo kernel só quando o "fora" é a mesma VM; no Windows o "fora" (Git Bash) não é Linux: o contraste correto é `uname -r` num contêiner × `wsl uname -r`/Desktop.
- Imagens oficiais verificadas hoje: `python:3.14-slim`, `python:3.13-slim`, `ubuntu:24.04`, `ubuntu:26.04`, `alpine:3.23`, `nginx:alpine` existem no Docker Hub (`docker buildx imagetools inspect`). A `ubuntu` oficial não traz Python (original errou ao usar imagem local).
- Docker Desktop: licença — grátis para uso pessoal, educação, pequenas empresas (<250 funcionários E <US$10 mi de receita), projetos open source não comerciais. https://docs.docker.com/desktop/setup/install/windows-install/

## Erros comuns
- "Contêiner é VM leve." / achar que isola tudo (leva software, não dados/segredos).
- `Cannot connect to the Docker daemon`: Engine parado/Desktop fechado.
- `docker stop` de 10 s com exit 137 quando o PID 1 ignora SIGTERM (aparece no original, ret. no cap. 4).
- Rodar o lab em Git Bash/Windows: `MSYS_NO_PATHCONV=1` e caminhos `/site` convertidos; usar `sh -c` com aspas e evitar `/` iniciais em argumentos (testar).
